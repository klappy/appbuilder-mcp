## Findings

### F-1 — METRICS list diverges from ptxprint-mcp; PR body's "verbatim mirror" claim is qualified (acceptable)

PR body §"Files added/modified" describes `src/snapshot.ts` as a "verbatim mirror" of ptxprint-mcp's snapshot.ts. The module API (interfaces, function signatures) is indeed verbatim per the parity table above. However, the METRICS list itself diverges:

| ptxprint-mcp METRICS | PR #10 METRICS | Notes |
|---|---|---|
| `pages_typeset_weekly` (hero) | replaced by `apk_bytes_weekly` | Correct rebinding |
| `successful_builds_weekly` | `successful_builds_weekly` | Same |
| `cache_hits_weekly` | (absent) | Not in spec; SAB lacks PTXprint's caching layer |
| `cache_misses_weekly` | (absent) | Same |
| `failure_mode_distribution_weekly` | `failure_mode_distribution_weekly` | Same |
| (absent) | `total_builds_weekly` | New, satisfies spec "build count" |

Spec P2.8 requires "at least four SAB-equivalent metric definitions" with the four named categories — all four present. The PR body acknowledges this in the METRICS table description ("METRICS table holds 4 metrics (see below)"). The "verbatim mirror" framing in the prose could be sharpened to "verbatim module API; SAB-flavored METRICS list" but the substantive contract is met.

Not a disposition driver. Cosmetic.

### F-2 — `wrangler deploy --dry-run` not run end-to-end (environmental, not PR-fault)

Spec P2.9 acceptance: "`wrangler deploy --dry-run` succeeds and the dry-run output includes the new binding and trigger."

Validator's container hit a Docker daemon dependency on a different binding (the build-job container image pull for `app-builders`). The wrangler.jsonc itself parses correctly:
- `wrangler types` regenerated `worker-configuration.d.ts` cleanly.
- `TELEMETRY_SNAPSHOTS: R2Bucket` is in the generated Env interface.
- `triggers.crons: ["0 0 * * 1"]` parses as valid wrangler config.
- The R2 binding is structurally identical to the existing `OUTPUTS` binding which already deploys successfully.

The PR body honestly disclosed: "`wrangler deploy --dry-run` is the validator's confirmation; the build session does not have CF auth to run it." The validator could not complete the dry-run either due to container/Docker setup, but the structural evidence is sufficient. **Recommend** a follow-up dry-run from a deployment-capable environment as part of merge confidence; not a blocking gap.

### F-3 — Live `wrangler dev` curl transcript substituted (soft gap)

Spec P2.10 acceptance: "PR body includes a curl transcript: one rejected request without the token, one accepted request that triggers `runSnapshotForWeeks()`."

PR body links to `docs/transcripts/feat-snapshot-mechanism.md` which contains a synthetic transcript captured by invoking `handleSnapshotRun` directly with synthetic Request objects (rather than against `wrangler dev`). The PR body acknowledges deferral ("Live wrangler-dev curl deferral" section). The 7 route-handler unit tests exercise the same handler the dispatcher uses; behavior is identical.

The substantive intent (evidence the route accepts/rejects correctly) is met. The PR-body curl-transcript text requirement is missed. Naming as a soft gap; the substitution is reasonable and durably in-repo.

### F-4 — **PR pre-applies an unmerged spec amendment (process-level pivot trigger)**

PR #10's "Bookkeeping change (per spec amendment)" section discloses:

> This PR adopts the pattern proposed in `BLOCKERS/SPEC-AMENDMENT-shared-state-conflicts.md` (filed on `chore/spec-amendment-shared-state`):
> - Per-PR work-log file at `docs/work-log/feat-snapshot-mechanism.md` (no edits to `docs/work-log.md`).
> - **No edits to `docs/parity-matrix.md`.** Validator owns the `open → in_review → closed` transition for the affected rows on accept.

Verified observations:
- PR #10 does NOT include `BLOCKERS/SPEC-AMENDMENT-shared-state-conflicts.md` (search across all branches finds it only on `chore/spec-amendment-shared-state`, 1 commit ahead of main, 4 behind).
- PR #10 does NOT edit `docs/parity-matrix.md` (verified: zero diff).
- PR #10 adds `docs/work-log/feat-snapshot-mechanism.md` (new file) instead of editing `docs/work-log.md`.

Per spec §6.2 SPEC-AMENDMENT protocol:

> The amendment is **not** applied. The build session continues with the next non-affected row. The validator session reviews the amendment as part of its disposition; if the validator agrees, the disposition is `pivot` and a follow-up `parity-spec-v2.md` is authored in a new spec session.

The amendment was filed at 2026-05-01T11:50Z explicitly stating "awaiting operator decision before commit + push." PR #10 was opened at 2026-05-01T11:55:31Z (5 minutes later) and pre-applied the amendment without operator ratification. This is a process violation: the build session is supposed to continue with the OLD pattern (or stop) until the validator session ratifies the amendment; instead it adopted the new pattern unilaterally.

**Validator's review of the amendment itself:** the amendment is sound. The shared-state pattern (`docs/parity-matrix.md` + `docs/work-log.md` edited by every build PR) creates O(N²) merge-conflict pressure across N concurrent PRs. PR #6, #7, #8, #9 all edited both files; the build session correctly identified the cumulative cost. The proposed pattern (per-PR work-log + validator-owned matrix transitions) eliminates the cross-coupling without losing any traceability — PR bodies still name matrix rows by ID, and validator merges include the matrix bump as part of the merge atom.

**However**, per spec §8.2, "If the validator believes the spec itself is wrong, the disposition is `pivot` (§6.2), not `iterate`." The proper disposition path is:

1. Validator (this finding) agrees with the amendment.
2. Disposition: `pivot`.
3. Recommend a fresh spec session to author `docs/parity-spec-v2.md` codifying the per-PR work-log pattern and validator-owned matrix transitions.
4. PR #10 re-validates against v2 — already structured per the amendment, will sail through.

## Disposition

**`pivot`** — validator agrees with the proposed spec amendment.

### Pivot rationale (per spec §8.2)

The current spec criterion (every build PR edits `docs/parity-matrix.md` and `docs/work-log.md`) is wrong: it produces O(N²) merge conflicts across concurrent build PRs without any throughput benefit. The amendment proposed in `BLOCKERS/SPEC-AMENDMENT-shared-state-conflicts.md` is structurally sound and pre-evidenced by PR #10 itself (which avoids the conflict pattern PRs #7 and #9 inherit).

### Recommended next steps

1. **Open a spec session** to author `docs/parity-spec-v2.md` with `supersedes: docs/parity-spec.md` per spec §6.3. The v2 codifies:
   - Build-session per-PR work-log files (`docs/work-log/<branch>.md`).
   - Build session does NOT edit `docs/parity-matrix.md`.
   - Validator owns matrix `status` transitions as part of the merge atom.
   - Existing matrix edits in PRs #6, #7, #9 are grandfathered (validator confirms bumps already present rather than requiring them).
2. **Open a small PR** for `BLOCKERS/SPEC-AMENDMENT-shared-state-conflicts.md` to bring the amendment file from `chore/spec-amendment-shared-state` into `main` for audit-trail durability.
3. **Re-validate PR #10 against v2** in a fresh validator session. The substantive code (P2.8–P2.11) is correct and complete; only the bookkeeping pattern needs the spec to bless it.

### What is and is not pivoted

- **Pivoted:** the bookkeeping criterion in spec §2 evidence form #1 + §6.1 cross-edit allowance, as it intersects with the per-gap loop in `docs/agent-prompts/02-build-session.md` §5–6.
- **Not pivoted:** any P2.8–P2.11 acceptance criterion. The substantive work is correct and the validator's structural review confirms readiness to ship.

### Why not `accept`

PR #10 cannot be `accept`-ed under the current spec because the current spec requires matrix edits and a shared work-log that this PR deliberately omits. Accepting would normalize bypassing §6.2 and weaken future amendment discipline.

### Why not `iterate`

`iterate` would mean asking PR #10 to re-introduce the shared-file edits, which re-introduces the conflict pattern the amendment is correctly solving. The build session has produced the right artifact; the spec needs to catch up. This is the textbook `pivot` case per §8.1: "If the validator believes the spec itself is wrong, the disposition is `pivot` (§6.2), not `iterate`."
